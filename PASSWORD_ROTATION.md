# Coordinated password rotation

The platform owns cluster ordering through authenticated `POST /credentials/rotate` requests to each data member's health server. Requests use Basic authentication (`railway`, current pinned password) and a JSON body with `operation`, `newPassword` and `currentPassword`. Successful responses contain `{ "version": 1, "leader": true|false }`. Phases are `preflight`, `prepare`, `database`, `member` and `verify`; each tolerates a repeated request after a lost response. Engine error bodies and credentials are never returned.

`database` updates the existing root user on the elected primary with majority write concern. `member` proves replication through a fresh authentication, swaps the shared client and persists the password pin. `key_prepare` rolls each secondary, then the current primary, with both derived keys; `key_commit` repeats with only the new key. The supervisor refuses to stop a primary until catch-up-aware stepdown succeeds. Durable pin intent survives process loss and every phase waits for the full set to return to PRIMARY/SECONDARY health. `key_status` lets the platform re-resolve the primary between passes. Internal peer clients follow the live pin and startup recovery proves staged credentials against the database. Verification checks replica-set health/majority, rejection of the old password, and that the running process and durable pin both contain only the new key. A restarted member can adopt a disjoint peer key only after proving a root credential against that live peer.

The platform preflights every member and writes private durable intent everywhere before changing the primary. It commits the root variable only after member adoption, then rolls coordination/proxy services and verifies every member. Pre-commit compensation uses the same protocol with the two passwords reversed. Journals are removed only after verification. A manual environment-variable edit alone is not evidence that database credentials changed.

Publish this image before enabling the companion backend workflow, and upgrade all data members of existing clusters. Templates and their variable references stay unchanged. Existing images without this endpoint are refused during platform preflight.

The rolling keyfile procedure follows [MongoDB's documented two-pass rotation](https://www.mongodb.com/docs/manual/tutorial/rotate-key-replica-set/). Each pass includes a primary stepdown. This requires two planned elections in the normal case, conflicting with the RFC's separate one-failover budget; resolve that requirement before production rollout.

Local integration test: build `mongo-wrapper`, install Python `pymongo`, then run `test/password-rotation-local.py` with `MONGOD` and `MONGO_WRAPPER` pointing at their binaries. It creates and cleans up an isolated three-member replica set, runs both passes and repeated requests, then compensates and verifies retained data.
